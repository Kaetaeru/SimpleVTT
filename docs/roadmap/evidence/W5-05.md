## Production queue and catch-up contract on the verified product tree

### 1. Live presentation sequence is monotonic and duplicate-safe

At product SHA `2ac28651312f1fdbe82edb74fd13f342a8f910f7`, `src/app/connectedSessionRuntimeAdapter.ts` accepts live remote presentation through `applyConnectedResolutionPresentation` only in Client mode and only after `isConnectedResolutionPresentation` validation.

A presentation with `delivery !== "live"` is rejected from the live channel because catch-up presentation must arrive with its committed event. A live presentation whose `presentationSequence` is less than or equal to `lastAppliedPresentationSequence` returns `duplicate` and is not enqueued or reinstalled. Only a strictly newer sequence advances the Client's presentation sequence.

This prevents duplicate/non-monotonic live transport from replaying a completed presentation as a new action.

### 2. Remote presentation stages are ordered, with stale replay cancellation on a newer dice signal

`enqueueOrInstallConnectedPresentation` installs the first presentation immediately. Later non-dice stages are appended to `pendingPresentations`; `advanceConnectedResolutionPresentation` consumes that queue with `shift()`, preserving insertion order.

When a newer remote dice presentation arrives, the runtime deliberately clears `pendingPresentations` and installs the new authoritative dice signal. This prevents stale result stages from an older replay from visually overtaking a newer committed roll.

`tests/ui/connectedResolutionPresentation.test.ts` directly fixes this behavior:

- a separate Client applies a live presentation once without mutating mechanics state;
- replaying the same sequence returns `duplicate` and leaves `lastAppliedPresentationSequence` unchanged;
- a later non-dice stage is queued and then advanced in order;
- a newer remote dice signal returns `replaced`, clears stale queued stages, and becomes the active presentation;
- the observer's mechanics state is unchanged by presentation-only application, proving no Client-side mechanics rerun is used to render the remote result.

### 3. Catch-up is committed Host history, not a second live resolution

`src/app/connectedActionRoutingAdapter.ts` builds the terminal presentation with delivery `catchup` from the already-authoritative completed Host resolution, attaches it to the committed `resolution` event payload together with the canonical `ResolutionEvent[]`, and broadcasts the Host-ledger `event-batch`.

On the Client, `applyConfirmedPayload` validates the embedded presentation, applies the committed resolution events, performs owner write-back, and then calls `enqueueOrInstallConnectedPresentation` on that same presentation payload. It does not call the action resolver or generate new dice. It records the event-derived Activity and advances `lastAppliedPresentationSequence` to at least the committed presentation sequence.

The live presentation entrypoint explicitly rejects `catchup` delivery, so terminal history cannot masquerade as a fresh live `resolution-presentation` message. Issue #111 independently records this policy as `terminal catch-up without reroll`; issue #114 records terminal catch-up retention in the remote queue.

### 4. Ordered event history and duplicate replay are exactly once

`src/app/connectedSessionProtocol.ts` makes `ClientSessionReplica` the ordered event-history boundary. Before payload application it:

- rejects a different Session;
- returns `duplicate` for an already-applied `eventId`;
- rejects a conflicting sequence at or behind the current cursor;
- rejects a gap unless `event.sequence === cursor + 1`.

The cursor advances only after payload application succeeds. `applyBatchAsync` processes events sequentially and stops on rejection. Therefore a catch-up resolution presentation can reach the presentation queue only through gap-free Host history and cannot reapply the same committed payload after its event ID has already been accepted.

### 5. Reconnect resumes from the accepted cursor

`src/app/connectedSessionRuntimeAdapter.ts` reconnects a Client by sending `hello` with `knownEventCursor = state.replica?.cursor ?? 0`. Host `hello` handling validates that cursor and returns `ledger.eventsAfter(knownEventCursor)` in `hello-ack`; the same cursor also backs explicit `catchup-request` handling.

`tests/ui/productionClientReconnect.test.ts` directly proves the production path: after reconnect, the Client sends the previously accepted cursor, applies the next `hello-ack` catch-up event once, and then ignores a replay of that same acknowledgement without advancing the cursor, duplicating Activity, or duplicating the local participant.

For resolution events, the same replica preflight surrounds the committed presentation payload, so reconnect replay cannot reapply the resolution state or reinsert its completed presentation as a new event.
