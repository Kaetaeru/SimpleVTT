# 캐릭터 시스템 재설계 — 생성 · 시트 · 가방 · 성장 (P1 + P2)

- 상태: **기획 v0.1 — 소유자 지시(2026-09-14) "검사를 할 바엔 제대로 기획해서 다시 만들자"에 따른 초안. 소유자 결정 D43~D52를 기다린다.**
- 자리: [전면 개편 설계](PRODUCT_RENOVATION.md) §5·§10의 P1(개인 캐릭터)·P2(생성과 성장)를 이 문서가 전개한다. 세션 쪽은 [테이블 런타임](TABLE_RUNTIME.md)·[규칙 런타임 명세](RULES_RUNTIME_SPECS.md), 할 수 있어야 하는 것의 목록은 [기능 인벤토리](CAPABILITY_INVENTORY.md) §2가 그대로 기준이다.
- 원칙이 충돌하면 [PRODUCT_RENOVATION.md](PRODUCT_RENOVATION.md)의 D1~D3, §12의 결정이 우선한다.

## 0. 이 문서의 규칙

- "규칙"은 SRD 5.2.1(2024 규칙)이다. 2014 규칙은 쓰지 않는다. 비SRD 본문(PHB 2024 등)은 저장소에 넣지 않고 설치 모듈로만 들어온다.
- 파생값은 저장하지 않는다. 사용자가 고른 것(원본)과 사용량(런타임)만 저장하고, 나머지는 한 함수가 계산한다(D3).
- 한 화면도 자기 계산을 갖지 않는다. 생성 미리보기·시트·레벨업 비교·세션 입장은 같은 계산 결과를 읽는다.
- 내장 SRD와 설치 모듈은 같은 카탈로그, 같은 id 형식, 같은 확장점을 쓴다. 내장 전용 지름길을 두지 않는다.
- 완료 기준은 "화면이 있다"가 아니라 §9의 전수 검사가 green이고 §3의 규칙 목록이 모두 동작·표시되는 것이다.

## 1. 왜 다시 만드는가 — 현재 구조의 결함

2026-09-14 소유자 실기기 검사에서 나온 세 가지는 각각 다른 결함이 아니라 같은 구조의 증상이다.

| 증상 | 직접 원인 | 구조적 원인 |
| --- | --- | --- |
| 레벨업 재주 목록에 기원 재주(내장·설치 모두)가 나온다 | `progressionRuntimeAdapter.featOptions`가 `category==="feat"` 전부를 넣고 tier를 보지 않는다. 같은 코드가 Phase 08 어댑터 12개에 복사돼 있다 | 규칙(재주 등급)이 카탈로그에 있지만 화면별 어댑터가 각자 목록을 만든다 |
| 시트에 종족 특성이 없다 | 시트는 `features` 문자열 토큰만 보여 주는데, 종족 정의의 `traits`는 생성 때 토큰으로 기록되지 않는다(인덱스에 `baseFeatures`가 있는 엘프·노움·티플링만 일부) | 특성이 "정의"가 아니라 "생성 때 남긴 한글 문자열"로 시트에 산다. 정의를 고쳐도 기존 캐릭터에 반영되지 않는다 |
| 드워프 강인함이 레벨업에 안 붙는다 | 생성 계산(`characterCreationV10Plan`)은 알고, 레벨업 계산(`domain/progression`)은 종족을 모른다 | 최대 HP를 두 곳이 따로 계산한다 |

같은 구조가 만드는, 아직 확인하지 않은 위험:

- 생성·시트·레벨업·세션 입장이 각각 파생값(HP, AC, 숙련, 슬롯, 공격)을 계산한다: `characterCreationV10Plan.ts`, `characterSheetV10Projection.ts`, `domain/progression.ts`, `table/actors.ts`.
- 생성·성장 코드가 `src/app` 36개 파일 약 8,100줄이고, Phase 08 어댑터 12개가 요청 객체를 복제한다. 한 규칙을 고치려면 13곳을 고친다.
- 참조 카탈로그(MockAdapter)는 짧은 id(`feat.alert`), 모듈은 긴 id(`dnd.srd521.feat.alert`)를 써서 같은 재주가 두 이름으로 존재한다.
- 설치 콘텐츠는 `setInstalledFeatEntries()` 같은 전역 배열로 옆에 붙어 있어, 어떤 경로는 보고 어떤 경로는 못 본다.
- §22.1~§22.3의 미결 항목(언어 자동 기록, 종족 특성 사용 횟수, 서브클래스 3레벨 특성 자동 부여, 멀티클래스 숙련, 재주 선행 조건, 주문 교체, 종족 5레벨 특성, 피해 저항 파생값)도 모두 "계산이 흩어져 있어서" 남은 것들이다.

결론: 낱개 수정으로는 같은 종류의 문제가 계속 나온다. 계산을 하나로 모으고 원본만 저장하는 구조로 다시 만든다.

## 2. 목표와 범위

**목표**: 플레이어가 원하는 레벨의 캐릭터를 만들고, 시트와 가방을 직접 다루고, 레벨업하고, 그 캐릭터로 V2 테이블에 앉으며, 그 모든 화면이 같은 규칙 계산 하나를 읽는다.

**범위 안**

- P1: 새 시트(디지털 탭 / 종이형, D1)와 가방. 사용량 인라인 수정, 원본은 편집 초안(D3). 개인 휴식.
- P2: 안내형/빠른 생성(같은 초안), 원하는 시작 레벨(D2), 레벨업, 원본 편집, 멀티클래스.
- 내장 SRD 5.2.1 전부(종족 9·배경 4·직업 12·SRD 서브클래스 12·재주 17·주문·장비)와 설치 모듈(종족·배경·재주·서브클래스·주문)이 같은 경로.
- 기존 저장본 이관과 되돌리기.
- 세션 입장 계약: 테이블이 시트에서 읽는 것과 세션이 시트에 되돌려 쓰는 것.

**범위 밖**(첫 출시): 다운타임·제작(§22.4), 탈것·물속·비행(D11), 캐릭터 간 거래 UI(파티 보관함은 기존 기능 유지), 자동 초상 생성.

## 4. 하나의 모델 — 원본 · 계산 · 사용량

```text
CharacterSource (사용자가 고른 것만)        ContentCatalog (SRD 모듈 + 설치 모듈)
        │                                            │
        └──────────► deriveCharacter(source, catalog) ◄──────────┘
                                │
                     DerivedCharacter (모든 파생값 · 저장하지 않음)
                                │
   CharacterRuntime (사용량) ────┼──── 화면: 생성 미리보기 · 시트(디지털/종이) · 레벨업 비교 · 가방
                                │
                        테이블 입장 (Actor 생성)  ──►  세션 write-back은 Runtime만 바꾼다
```

### 4.1 `CharacterSource` — 원본

저장되는 것은 이것과 §4.4의 런타임뿐이다.

```text
identity      id, name, portrait, alignment, notes(외형·성격·배경 서술)
rules         rulesProfile{id, version}, contentModules[{moduleId, version}]   // 계산에 쓴 카탈로그 고정
origin        species{id, choices{}}, background{id, abilityBonus{+2/+1 또는 +1/+1/+1}, choices{}}
abilities     method(point-buy | standard-array | manual), base{str..cha}       // 배경·재주 보정 전
languages     chosen[]                                                          // 자동 언어는 계산
tracks[]      획득 순서대로 { classId, level, hp{fixed | roll:n}, choices{} }    // 레벨 기록 하나 = 레벨 하나
              choices 예: subclass, asiOrFeat{asi{+2 | +1+1} | feat{id, abilityChoice}}, skills, expertise,
                          fightingStyle, weaponMastery[], cantrips[], prepared[], spellbook[], swap{from,to},
                          invocations[], metamagic[], languages[], tools[]
equipment     startingChoice(loadout | gold), 초기 장착
xp            number (D34, 캠페인이 XP일 때)
```

- `tracks`는 멀티클래스 획득 순서 그 자체다. `level=10` 복사가 아니라 레벨 기록 10개다(D2).
- 어떤 선택이 필요한지는 원본이 아니라 계산이 결정한다(§4.3). 원본에는 답만 있다.
- 원본을 바꾸는 유일한 경로는 "편집 초안 → 재계산 → 비교 → 저장"이다(D3). 시트의 인라인 조작은 원본을 건드리지 않는다.

### 4.2 `ContentCatalog` — 내장과 설치의 통합

- `content/modules/*`(SRD)와 설치 문서(`InstalledContentDocumentV1`)를 **같은 스키마**로 읽는 하나의 서비스. 전역 `setInstalled*Entries()`는 없앤다.
- id는 항상 긴 형식 하나(`dnd.srd521.feat.alert`, `x.phb.feat.…`). 참조 카탈로그의 짧은 id는 이관 시 정규화한다.
- 정의 종류(모두 기존 확장점을 그대로 씀): `class`(표·특성·숙련·주문 시전 모드), `subclass`(extends class, 레벨 특성), `species-definition`(크기·속도·암시야·traits·choices·semantics), `background-definition`(능력치·기술·도구·originFeat·장비), `feat-definition`(**tier**·선행·능력치 증가·grants·execution), `spell-definition`/`spell-mechanic`, `common-play`, 장비.
- 특성 텍스트(한글 설명)는 정의에 붙어 있어야 한다. SRD 종족 특성 설명(`dwarven-toughness` 등 30여 개)은 origins 모듈에 presentation으로 추가한다. 설치 모듈은 컴파일러가 이미 붙인다.
- 미지원 콘텐츠는 "설명만 / 수동 운용 / 자동 실행" 상태를 정의에 갖고, 생성을 막지 않는다(인벤토리 §2.1).

### 4.3 `deriveCharacter` — 계산 하나

입력은 원본과 카탈로그, 출력은 `DerivedCharacter`와 **필요한 선택 목록**이다. 계산은 기존 도메인을 재사용한다: `domain/progression*`(레벨 표·선택 정의), `coreClassResources`, `multiclassSpellSlots`, `featRuleCatalog`, `weaponRuleCatalog`, `conditions`, `spellcasting`.

1. **부여 원장(grant ledger)**을 만든다. 종족 → 배경 → 레벨 기록 순서대로, 각 출처가 주는 것을 한 줄씩 적는다: `{source, level, kind, value}`. kind: `trait`(종족 특성), `feature`(직업 특성), `proficiency`(내성·기술·갑옷·무기·도구·언어), `hp-per-level`, `speed`, `sense`, `size`, `resource`(풀·회복), `spell`(소마법·준비·항상 준비·주문서), `slot-table`, `feat`(등급 포함), `mastery-count`, `attack`, `defense`(저항·면역·취약), `choice-needed`.
2. **필요한 선택**은 원장의 `choice-needed` 가운데 원본 `choices`에 답이 없는 것이다. 생성 마법사와 레벨업 화면은 이 목록을 그대로 렌더링한다. 후보 목록도 여기서 만든다(예: ASI 재주 후보 = 카탈로그의 `feat` 중 `tier==="general"`이고 선행 조건을 만족하는 것, 불가 이유 포함).
3. **파생값**은 원장을 접어서 얻는다.
   - 최대 HP = Σ레벨(히트 다이스 값 + 건강 수정치, 최소 1) + Σ`hp-per-level` × 총 레벨 + 상수 보정. 건강 변화는 자동으로 소급된다(레벨마다 다시 계산하므로 "소급" 코드가 따로 없다).
   - AC = 장착 갑옷 공식 vs 비무장 방어(먼저 얻은 직업) vs 효과, 큰 값. 방패 +2.
   - 숙련 보너스(총 레벨), 내성·기술(숙련·전문화), 패시브 지각, 이니셔티브, 이동 속도(종족 + 특성 + 갑옷 근력 미달 −10), 감각.
   - 주문: 직업별 시전 능력치·DC·명중, 슬롯(합산 표 + 계약 마법 별도), 소마법/준비 수, 항상 준비.
   - 공격: 장착·소지 무기별 명중·피해·속성·통달(선택한 통달만 활성), 맨손 타격.
   - 자원 풀: 직업·종족·재주 사용 횟수와 회복 조건(§22.2 종족 특성 사용 횟수 포함).
   - 특성·재주·주문·언어·도구·저항 목록(설명 포함).
   - 멀티클래스 중복 규칙(추가 공격 최댓값 하나, 비무장 방어 하나, 신성 변환 풀 공유)은 접는 단계의 규칙이다.
4. **검증**: 능력치 상한, 포인트 바이 합, 멀티클래스 선행 조건, 재주 선행 조건, 장비 숙련 없는 갑옷 경고. 결과는 `blocking[]`/`warnings[]`.

이 함수 하나가 생성 미리보기, 시트, 레벨업 비교(전/후 두 번 호출해 차이), 세션 입장(Actor 생성)에 쓰인다. **다른 어느 곳도 HP·AC·슬롯을 계산하지 않는다.**

### 4.4 `CharacterRuntime` — 사용량

```text
hp{current, temporary}, slotsUsed{level: n}, pactSlotsUsed, resources{poolId: current}, hitDiceUsed{dN: n},
deathSaves{s, f}, lifeFlags{stable, unconscious, dead}, exhaustion, inspiration, conditions[], effects[],
inventory[{instanceId, definitionId, quantity, charges, equipped, wieldSlot, attuned, container, name, note}], gold,
lastSession{sessionId, at}
```

- 시트의 인라인 조작과 세션 write-back은 여기만 바꾼다. 최댓값은 언제나 `DerivedCharacter`에서 온다.
- 범위를 벗어난 값(슬롯 5/4)은 거부하고 이유를 보이며, 원본을 고칠 경로를 안내한다. 몰래 자르지 않는다.
- 조율·탈진·상태도 여기 있으므로, 지금 미뤄 둔 write-back 항목(탈진·조율)이 자연히 들어온다.

### 4.5 저장 형식 v2와 이관

- 레코드 = `{ schema:2, source, runtime, cache?{derived, catalogFingerprint} }`. `cache`는 목록 화면 표시용이고 언제든 버릴 수 있다.
- V1 레코드(`source.build + progression + materializedCache.sheet`)는 **읽기 전용으로 보존**하고, 이관기가 v2 원본을 재구성한다: 직업·레벨·서브클래스·능력치·배경·종족·재주·주문·아이템·자원·HP 선택(있으면)을 옮기고, 재구성할 수 없는 선택(예: 레벨별 HP 굴림값)은 "고정값으로 간주"로 표시해 사용자가 편집 초안에서 바로잡게 한다. 이관 보고서를 캐릭터마다 남긴다.
- 이관은 백업 복사본과 fixture로 먼저 검증하고, 원본 파일을 덮어쓰지 않는다(PRODUCT_RENOVATION §10 저장본 보호). V1 레코드가 남아 있는 한 되돌리기가 가능하다.
- 접속 중인 캐릭터의 개인 수정은 live actor를 덮어쓰지 않고 revision 충돌로 제시한다(인벤토리 §2.6).

### 4.6 테이블 계약

세션 입장은 `DerivedCharacter + CharacterRuntime → Actor`다. 테이블이 지금 시트에서 읽는 것(`items`·`abilities`·`proficiencyBonus`·`speed`·`resources`·`classLevels`·`level`·`hp`·`durableLifeFlags`·`tempHp`·`hitDiceByDie`·`weaponMasteryIds`·`spellSlotMaximums`·`skills`·`preparedSpells`·`cantrips`·`saves`·`attacks`·`ac`)은 모두 파생값이거나 런타임이다. 전환 뒤 `table/actors.ts`는 `CharacterSheet`가 아니라 이 둘을 받고, 되돌려 쓰는 것은 런타임뿐이다(HP·임시 HP·슬롯·자원·히트 다이스·죽음 내성·안정·사망·탈진·조율·상태·아이템 수량·금화).

## 5. 흐름

### 5.1 생성 (안내형 / 빠른 편집, 같은 초안)

1. 기본: 이름, 규칙 프로필, **시작 레벨**(D2), 성장 방식은 캠페인이 정하므로 묻지 않는다.
2. 직업 → 기원(배경·종족) → 능력치 → 언어·세부 → 장비 → 레벨별 선택(시작 레벨이 1보다 크면 레벨 기록을 순서대로 채운다) → 검토.
3. 각 단계는 `deriveCharacter`의 "필요한 선택"을 보여 준다. 종족·배경·직업을 바꿔도 무관한 답은 유지된다(답은 출처별 key로 저장).
4. 검토 화면은 완성된 시트 그대로다(같은 컴포넌트). 막힘(blocking)이 없으면 저장 한 번.
5. 초안은 자동 저장되고 확정본과 분리된다. 취소·재시작 가능.
6. 빠른 편집은 같은 초안을 한 화면에 펼친 것이다. 별도 데이터 경로 없음.

### 5.2 레벨업

1. 새 레벨 기록을 `tracks`에 붙인다(멀티클래스면 직업 선택, 선행 조건 검사).
2. HP: 고정값 기본, 굴림은 앱 주사위로(결과 기록). 
3. 필요한 선택만 묻는다(서브클래스·ASI/재주·주문·통달·전문화·기원술 등). 후보는 §4.3의 규칙으로 걸러진다.
4. 비교: 전/후 `DerivedCharacter` 차이(최대 HP·숙련·슬롯·특성·자원·공격)를 표로. 저장 한 번. 반쪽 레벨업 없음.
5. 세션 중에는 DM이 허용한 시점(장면 전환·휴식)에만, 그 외에는 예약(인벤토리 §2.4).

### 5.3 원본 편집 (D3)

시트의 "편집" → 초안(원본 복사) → 바꾸기(능력치·레벨별 HP 선택·숙련·언어·도구·출처·이름) → 비교 → 저장. 파생값 직접 입력은 없다. `AC +2` 같은 임의 오버라이드는 만들지 않는다.

### 5.4 시트와 가방

- 디지털 탭 시트와 종이형 시트(D1)는 같은 `DerivedCharacter + Runtime`을 다른 배치로 그린다. 선호는 사용자 설정.
- 탭: 개요(HP·AC·속도·감각·숙련·내성·기술), 행동(공격·주문·특성 사용), 특성(직업·종족·재주·배경), 주문, 가방, 상태·기록.
- 가방: 카탈로그 검색 추가, 사용자 아이템, 메모형, 수량·충전, 같은 정의의 인스턴스 구분, 장착·손·조율 슬롯, 컨테이너, 파티 보관함 이동, "수량 수정"(관리)과 "물약 마시기"(규칙 행동, 세션 밖 즉시 적용·기록) 구분.
- 개인 휴식: 짧은(히트 다이스)·긴(HP·슬롯·자원·탈진 1) — 세션 안 휴식과 같은 함수.
- 계산 확인용 굴림: 기록되지만 상태를 바꾸지 않는다.

### 5.5 설치 콘텐츠

- 콘텐츠 화면에서 설치한 모듈은 카탈로그에 합쳐진다. 생성·시트·레벨업·세션 타일이 같은 카탈로그를 읽으므로 "설치는 됐는데 어디서는 안 보임"이 구조적으로 사라진다.
- PHB 2024 모듈은 비공개 파일이므로 저장소에는 같은 형식의 합성 픽스처(종족 1·배경 1·기원 재주 1·일반 재주 1·서브클래스 1·주문 2)로 검사하고, 실제 파일은 소유자 기기에서 §9.3 체크리스트로 확인한다.

## 9. 검증 계획

### 9.1 자동 전수 검사 (C1의 완료 조건)

- **행렬**: SRD 종족 9 × 직업 12 × 배경 4, 각각 1→20레벨. 선택은 결정적 기본값(첫 후보)으로 채운다.
- **골든 값**: 레벨별 최대 HP(고정값, 건강 14 기준, 종족 보정 포함), 숙련 보너스, 히트 다이스, 주문 슬롯 표(합산·계약 마법), 소마법·준비 수, 무기 통달 수, 특성 목록(레벨 표), 재주 선택 시점과 후보 등급, 서브클래스 시점, 종족 특성(`@5` 포함), 저항, 언어 수, 기술 수. 골든 값은 SRD 표에서 스크립트로 만들고 파일로 저장한다.
- **불변식**: 파생값을 저장하지 않는다(레코드에 HP 최댓값 없음), 어떤 화면 코드도 계산 함수를 import하지 않고 결과만 받는다(경계 검사에 규칙 추가), 짧은 id 없음.
- **멀티클래스**: 파이터 5/로그 3, 클레릭 2/팔라딘 3, 워락 3/소서러 2 같은 대표 조합의 슬롯·추가 공격·신성 변환.
- **설치 모듈**: 합성 픽스처의 종족·배경·기원 재주·일반 재주·서브클래스·주문이 생성·레벨업·시트·테이블 타일까지 흐른다. 기원 재주는 ASI 후보에 없다.

### 9.2 화면 검사

- 각 화면의 정적 렌더 테스트(워크스페이스와 같은 방식)와 Chromium 캡처. "계산됐지만 안 보임"을 막기 위해, 캡처마다 §3.3의 표시 항목을 셀렉터로 확인한다.

### 9.3 실기기 체크리스트 (소유자, Windows exe)

- PHB 모듈 설치 → 모듈 종족·배경으로 3레벨 생성 → 시트에 종족 특성·기원 재주 표시 → 4레벨 레벨업에서 일반 재주만 후보 → 드워프 최대 HP 레벨당 +1 → 세션 입장 → HP 변화 → 앱 재시작 → 유지.
